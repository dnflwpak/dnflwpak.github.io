문제
단말기 결제는 승인돼 고객은 카드 승인 문자를 받았지만 CRM에는 반영되지 않는 누락이 매달 약 10건(총 결제의 약 1%) 생겼습니다. 운영팀이 누락 건을 매번 수동으로 보정하는 것을 보고 개선을 직접 제안했습니다.
확인
테스트 단말기와 로그로 실패를 재현하고 토스와 함께 원인을 찾으며 PG 승인 후 반영 실패, 분할결제 중 취소, 결제 화면 이탈 등 실패 경로를 구분했습니다. 요청·승인·복구·실패 단계를 구조화된 JSON으로 남기는 trace API도 추가했습니다.
해결
실패 경로마다 끊긴 결제를 복구하는 흐름을 만들었습니다. 완료 응답 대신 취소가 오거나 대기가 길어지면 승인 결과를 조회해 완료 처리로 잇고, PG 승인 뒤 CRM 반영에 실패하면 즉시 취소하던 흐름을 완료 요청 재시도와 동기화 실패 보고로 바꿨습니다. 결제수단 선택 화면의 뒤로가기·타임아웃과 실제 취소를 구분해 분할결제에서 먼저 성공한 결제 내역을 보존했습니다. 환불 수단·이력 처리를 같은 DB 트랜잭션으로 묶고 승인번호가 없는 현금 환불 경로를 분리했으며 관련 테스트를 추가했습니다. 토스 권고에 따라 통합결제와 현금결제 경로를 분리하고 플러그인·API·화면의 동시 배포를 조율했습니다.

CRM DB 통합

메먼트 · 2026, AWS RDS·Aurora·DMS

문제
두 브랜드가 RDS를 5개씩 운영했지만 CPU 사용률은 평소 3% 이하, 최대 트래픽 때도 5% 미만이어서, 비용과 효율을 위해 통합을 직접 제안했습니다. MySQL 5.7 지원 연장 비용과 분산된 DB의 관리 부담도 커지고 있었습니다.
확인
기존 DB마다 여러 지점이 섞여 있고 지점별 스키마가 통일돼 있지 않아, 지점마다 database를 나누는 구조로 이관하기로 했습니다.
해결
통합 구조와 전환 계획을 문서로 정리해 승인받았습니다. DMS로 MariaDB·MySQL 운영 데이터를 실시간 동기화하고 MySQL 8 예약어(grouping, rank 등) 관련 코드를 고쳤습니다. 테이블·데이터 정합성과 개발 환경 기능을 검증한 뒤 병원 영업 종료 후 지점별로 순차 전환했고, 2026년 7월 뮤즈 전 지점 적용을 마쳤습니다.
결과
RDS 10개를 브랜드별 Aurora 클러스터 2개(쓰기·읽기)로 통합해 관련 DB 비용을 약 70% 줄였고, 전 지점 합산 다운타임은 10분 이내였습니다.

포잉 · 2017, PHP·MySQL·Redis·SQS

문제
전체 마케팅 푸시나 인기 레스토랑 예약 오픈 때 RDS CPU 100%와 DB 연결 초과로 서비스가 다운돼, 이벤트 제휴도 부담스러운 상황이었습니다.
확인
이벤트 때 사용자가 몰리는 홈 화면을 가장 유력한 원인으로 보고 로그로 확인했습니다. 홈 화면 SQL에는 무겁거나 튜닝할 쿼리가 없어, 쿼리가 아니라 조회 횟수 자체가 문제라고 판단했습니다.
해결
홈 화면 API 응답을 지역별로 Redis에 미리 적재해 DB를 거치지 않게 했습니다. 홈에 노출되는 콘텐츠가 바뀌면 SQS에 쌓고, Jenkins의 별도 배치가 큐를 반복해 가져와 Redis를 비동기로 갱신했습니다. ALB·Auto Scaling을 적용하고, Auto Scaling이 따라가지 못하는 순간 유입은 오픈 전 사전 증설로 보완했습니다.
결과
이벤트 때 반복되던 DB 다운이 사라졌고, 이벤트 제휴를 부담 없이 진행할 수 있게 됐습니다.

결과
B2C 앱과 포잉 OS가 하나의 결제 API를 함께 쓰게 되어, 결제 수단을 추가할 때 두 서비스를 따로 고칠 필요가 없어졌습니다.

결과
일정 조건 검색을 서비스에 도입했고, 응답 시간도 약 0.1초에서 0.05초로 줄었습니다.
